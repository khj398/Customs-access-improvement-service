## 5. 집필 시 금지·주의 표현 (계획서 8장)

| 대상 | 문제 | 조치 |
|---|---|---|
| "분류 정확도 100%" | 자동 결과와 일치하는 50건만 라벨링한 수치. 선택 편향 | **E05 결과로 교체.** 불가 시 "라벨링 완료 50건 한정" 조건 병기 |
| "유니패스 공개 API 활용" | 실제로는 포털 내부 AJAX 응답을 Playwright 로 수집 | "웹 자동화 기반 수집"으로 수정 |
| FAQ 챗봇 · 커뮤니티 게시판 | 2차 발표에서 언급했으나 미구현 | 기능으로 기술 금지. 향후 과제로만 언급 |
| "응답시간 300ms 달성" | 측정 기록 없음 | **E10 수행 후 기재**하거나 향후 과제로 이동 |
| `docs/SEARCH_ENGINE_DESIGN.md` 의 API 명세 | 레거시 FastAPI(`backend/`) 기준 | 현재 운영 백엔드(`cais_back`, `/api/…`) 기준으로 작성 |
| Lambda Function URL · DB 비밀번호 | 공개 저장소에 노출된 자격 정보 | 본문·부록·스크린샷 어디에도 포함 금지 |

### 코드·문서 불일치 목록 (집필 중 참고)

1. `--openai-target-level` 기본값이 설계서(2)와 코드(3)에서 다름 → **E13 으로 확정**
2. `itemModel.js` 의 `findByMonth()` 가 폐기된 별도 DB(`app_user.user_watchlist_target`)를 참조
3. README 가 존재하지 않는 `cais_front/STRUCTURE.md` 를 링크
4. `classification/README.md` 의 `classify_with_openai()` 는 현재 `OpenAIClassifier.classify()` 로 리팩터링됨
5. `etl/README.md` 는 `MYSQL_*` 환경변수를 안내하나 코드는 `DB_*` 를 읽음

## 7. 결과 해석 원칙

- E05 정확도가 80%대로 나와도 그대로 쓴다. 100%보다 훨씬 강한 결과다.
  라벨링 절차(블라인드·3인·유보 없음·라벨러 간 일치도)를 4.2절에 한 문단으로 기술하면
  그 자체가 방법론적 기여가 된다.
- E10 에서 규모가 작아 차이가 드러나지 않으면 그 사실을 정직하게 쓰고,
  1만 건 이상에서의 확장성은 향후 과제로 넘긴다.
- E04 에서 3자 질의가 보정되지 않는 것은 Meilisearch 설정상 정상이다.
  한계를 함께 적는 편이 설정을 이해하고 있다는 근거가 된다.
- E06 은 참가자 수가 적으므로 "통계적으로 유의하다"는 표현을 쓰지 않는다.

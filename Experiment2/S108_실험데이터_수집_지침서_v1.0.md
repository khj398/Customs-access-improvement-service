# S108 졸업논문 실험 데이터 수집 지침서 v1.0

**이 문서는 코딩 에이전트가 읽고 실행하는 작업 지침서다.**
문서를 건네준 사람(이하 **사용자**)은 이 문서를 읽지 않았을 수 있다.
따라서 사용자에게 "요청서에 있듯이"라고 말하지 말고, 필요한 것은 그때그때 직접 물어라.

## 0. 작업 개요

### 0.1 배경

이 저장소는 관세청 유니패스 세관 공매 데이터를 수집·자동분류·검색하는 시스템이다.
현재 이 시스템을 소재로 한 **졸업논문 초고(v1.0, 4쪽)가 이미 작성되어 있고**,
4장 평가 절의 일부 수치가 비어 있다. **너의 임무는 그 빈 수치를 채우기 위한
측정 데이터를 DB와 검색 엔진에서 추출하는 것이다.**

논문 집필은 다른 사람(편종윤)이 별도 환경에서 수행한다.
너는 **측정만 하고 결과 파일을 만들어 사용자에게 넘긴다.** 논문을 쓰지 않는다.

### 0.2 너의 역할 경계

| | |
|---|---|
| 해야 할 일 | SQL 조회, 검색 실험 재실행, 결과 파일 생성, 이상 징후 보고 |
| 해도 되는 일 | `Additional_Experiment/` 이하 측정 스크립트 수정 (§1.2 조건 하에) |
| **절대 하면 안 되는 일** | 분류·검색 **동작**을 바꾸는 모든 행위 (§1.1) |

### 0.3 완료 정의 (Definition of Done)

아래 5개 산출물이 §7 명세대로 생성되고, §8 커밋이 끝나면 완료다.

```
paper_eval_20260831/
├─ ground_truth_v2.csv          (100행)          ★★★
├─ accuracy_report.txt                            ★★★
├─ search_query_counts.csv      (40행)            ★★

```

우선순위가 낮은 것을 못 끝내도 된다. **`ground_truth_v2.csv` 하나만 나와도
논문의 가장 큰 구멍이 메워진다.** 시간이 부족하면 A → B → C 순으로 진행하고,
못 한 것은 솔직히 못 했다고 보고하라.

## 1. 불변 규칙

### 1.1 절대 수정 금지 파일

**아래 파일이 하나라도 변경되면 논문에 이미 실린 수치가 전부 무효가 된다.**
논문은 "이 코드 상태에서 측정했다"는 전제 위에 서 있다. 측정 도중에 코드가 바뀌면
어느 수치가 어느 코드에서 나왔는지 특정할 수 없어져 재현성이 무너진다.

```
classification/rules.yaml
classification/synonyms.yaml
classification/build_classification.py
classification/run_classification.py
classification/load_synonyms.py
classification/eval/evaluate.py
db/seed_category.sql
db/seed_category_extend.sql
db/seed_synonym.sql
db/seed_synonym_extend.sql
db/schema_*.sql
cais_back/models/meiliModel.js
cais_back/config/meili.js
cais_back/scripts/sync_meili.js
```

**작업 중 이 파일들에서 버그나 개선점을 발견해도 고치지 마라.**
발견한 내용은 `확인결과.txt`의 `[발견한 문제]` 항목에 기록만 하고 넘어가라.
이건 능력의 문제가 아니라 실험 설계의 문제다. 고치는 순간 측정 기준점이 사라진다.

특히 다음 유혹을 경계하라. 실제로 이 저장소에는 아래 결함이 **알려진 채로 남아 있고,
논문에 결함으로 서술되어 있다.** 고치면 논문 서술과 코드가 어긋난다.

- `rules.yaml`의 한글 키워드가 어절 경계 없이 부분 문자열로 매칭된다
  (예: 귀금속 제품명의 "에센스"가 화장품 규칙에 걸린다)
- 규칙 우선순위가 상위 개념 먼저라서 더 구체적인 소분류로 가지 못하는 경우가 있다
- RAW 토큰이 `[^A-Z0-9]+` 로 분리되어 한글 물품명에서는 사실상 생성되지 않는다

### 1.2 금지 행위

| 금지 | 이유 |
|---|---|
| `run_classification.py` 등 **재분류 실행** | DB의 `item_classification`이 갱신되어 논문의 커버리지 수치(rule 437 / openai 357)와 어긋난다 |
| **토큰 재적재** (`load_synonyms.py`, `sync_meili.js` 등) | 같은 이유. `item_search_token`이 바뀌면 검색 실험 결과가 달라진다 |
| **스키마 변경** (`ALTER`, `DROP` — `eval_label` 임시 테이블 제외) | 원본 데이터 훼손 |
| **NULL 값 채우기·삭제** | NULL 자체가 "파이프라인이 놓친 물품"이라는 측정 결과다 |
| **측정값 조정·반올림·보정** | 값이 나쁘게 나와도 그대로 보고하라. §5.2 참조 |
| 요청되지 않은 리팩터링·포매팅·의존성 업데이트 | `git diff`를 오염시켜 §8 검증이 불가능해진다 |
| 실패를 우회하는 임의 대체 구현 | §1.3 |

## 3. 단계 A — 표본 100건 채점 입력 추출 ★최우선★

### 3.1 왜 이 작업이 필요한가

저장소에 있는 `classification/eval/ground_truth.csv`는 93건 중 50건만 라벨링되어 있고,
그것으로 산출된 **"분류 정확도 100%"는 논문에 쓸 수 없다.** 라벨러가 애매한 건을
비워둔 채 쉬운 것만 남겨서 정확도가 구조적으로 부풀려졌기 때문이다.
심사에서 가장 먼저 깨질 지점이다.

그래서 새 표본 100건을 **빈칸 없이** 전수 라벨링했다. 그 정답 라벨에 시스템의
자동 분류 결과를 붙이는 것이 이 단계의 목적이다.

| | |
|---|---|
| 모집단 | 저장소 스냅샷 `unipass_all_2b.json` + `unipass_all_2c.json` (복합 PK 중복 제거 후 497건) |
| 추출 | `random.Random(42)` 무작위 100건 |
| 구성 | 수입화물 26 / 휴대품 74 (모집단 비율 23.5 : 76.5과 일치) |

DB의 794건이 아니라 신규 수집분 497건에서 뽑았다. 나머지 297건은 이전 수집 주기부터
DB에 누적되어 있던 것이라 저장소 스냅샷에 존재하지 않는다. **표본을 다시 뽑지 마라.**

### 3.2 입력 파일

사용자가 `label_sample_100_FINAL.csv` (UTF-8 BOM)를 가지고 있다. 컬럼:

```
no, pbac_no, pbac_srno, cmdt_ln_no, cargo_type, cmdt_nm, true_category_path, label_depth, note
```

### 3.3 임시 테이블 생성

```sql
DROP TABLE IF EXISTS eval_label;
CREATE TABLE eval_label (
  no                 INT,
  pbac_no            VARCHAR(20),
  pbac_srno          VARCHAR(20),
  cmdt_ln_no         VARCHAR(10),
  cargo_type         VARCHAR(20),
  cmdt_nm            VARCHAR(255),
  true_category_path VARCHAR(200),
  label_depth        INT,
  note               VARCHAR(500),
  PRIMARY KEY (pbac_no, pbac_srno, cmdt_ln_no)
) CHARACTER SET utf8mb4;
```

### 3.4 적재

`pbac_no`, `pbac_srno`, `cmdt_ln_no`는 **반드시 문자열로 적재하라.**
숫자로 변환하면 앞자리 0이 사라져 조인이 전부 실패한다.

```sql
LOAD DATA LOCAL INFILE '<절대경로>/label_sample_100_FINAL.csv'
INTO TABLE eval_label
CHARACTER SET utf8mb4
FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
LINES TERMINATED BY '\n'
IGNORE 1 LINES
(no, pbac_no, pbac_srno, cmdt_ln_no, cargo_type, cmdt_nm,
 true_category_path, label_depth, note);
```

`LOAD DATA LOCAL INFILE`이 서버 설정으로 막혀 있으면 파이썬(`pymysql` + `executemany`)으로
적재해도 된다. 그 경우에도 PK 3개 컬럼을 문자열로 유지하라.
CSV의 BOM 때문에 첫 컬럼명이 깨지면 파이썬에서 `encoding='utf-8-sig'`로 읽어라.

### 3.5 적재 검증 — **게이트**

```sql
SELECT COUNT(*) AS 적재건수 FROM eval_label;                  -- 반드시 100

SELECT COUNT(*) AS DB미존재 FROM eval_label l
LEFT JOIN auction_item ai USING (pbac_no, pbac_srno, cmdt_ln_no)
WHERE ai.pbac_no IS NULL;                                      -- 반드시 0
```

**100 / 0이 아니면 HALT.** 진행하지 마라.
0이 아닌 경우 아래로 원인을 좁힌 뒤 사용자에게 보고하라.

```sql
SELECT l.no, l.pbac_no, l.pbac_srno, l.cmdt_ln_no, l.cmdt_nm
FROM eval_label l
LEFT JOIN auction_item ai USING (pbac_no, pbac_srno, cmdt_ln_no)
WHERE ai.pbac_no IS NULL;
```

흔한 원인은 **CSV가 엑셀에서 저장되며 `pbac_no`가 `3.92602E+12` 지수표기로 깨진 것**이다.
실제로 한 번 발생했다. 이 경우 사용자에게 원본 CSV를 다시 받아라.
**절대 값을 추측해서 복원하지 마라.**

### 3.6 채점 입력 추출

```sql
SELECT l.no,
       l.pbac_no, l.pbac_srno, l.cmdt_ln_no,
       ai.cmdt_nm,
       CONCAT_WS(' > ', cg.name_ko, cp.name_ko, cl.name_ko) AS auto_category_path,
       ic.confidence  AS auto_confidence,
       ic.model_name  AS auto_model,
       ic.model_ver   AS auto_model_ver,
       ic.rationale   AS auto_rationale,
       l.true_category_path,
       l.label_depth,
       'PJY' AS labeler,
       l.note
FROM eval_label l
JOIN auction_item ai USING (pbac_no, pbac_srno, cmdt_ln_no)
LEFT JOIN item_classification ic USING (pbac_no, pbac_srno, cmdt_ln_no)
LEFT JOIN category cl ON cl.category_id = ic.category_id
LEFT JOIN category cp ON cp.category_id = cl.parent_id
LEFT JOIN category cg ON cg.category_id = cp.parent_id
ORDER BY l.no;
```

**`rationale` 컬럼을 반드시 포함하라.** 규칙이 어떤 키워드로 매칭했는지가 들어 있어
논문 5장 오분류 유형 분석의 직접 근거가 된다. 길다고 자르지 마라.

**`auto_*` 컬럼이 NULL인 행이 있어도 그대로 두라.** 채우지도, 지우지도 마라.
NULL은 "분류 파이프라인이 이 물품을 처리하지 않았다"는 측정 결과다.

→ 산출물: **`ground_truth_v2.csv`** (100행, UTF-8, 위 컬럼 순서 그대로)

### 3.7 채점 스크립트 실행

```bash
python classification/eval/evaluate.py \
  --gt classification/eval/ground_truth_v2.csv --save
```

→ 산출물: **`accuracy_report.txt`**

**경고 — `evaluate.py`를 고치지 마라.**

정답 라벨 100건 중 9건은 카테고리 트리에 대응하는 소분류가 없어 대분류 또는
중분류까지만 부여되어 있다. `label_depth` 컬럼으로 구분된다.

| label_depth | 건수 | 예 |
|---|---|---|
| 1 (대분류만) | 3 | `전자·전기`, `산업·장비` |
| 2 (중분류까지) | 6 | `가전 > 생활가전` |
| 3 (소분류까지) | 91 | `뷰티·위생 > 화장품 > 스킨케어` |

이 9건은 **라벨 깊이까지만 비교하는 접두 일치(prefix match)** 로 채점해야 옳다.
`evaluate.py`가 전체 경로 완전 일치만 본다면 9건이 전부 오답 처리되어 정확도가
부당하게 낮게 나온다.

**그럼에도 스크립트를 고치지 마라.** 완전 일치 기준 결과를 그대로 산출하고,
`확인결과.txt`에 "완전 일치 기준"이라고 명시하라.
접두 일치 채점은 `ground_truth_v2.csv`만 있으면 논문 작성 측에서 다시 계산한다.
스크립트를 고치면 그 결과가 어떤 기준으로 나온 것인지 검증 불가능해진다.

`evaluate.py` 실행이 실패하면 원인만 기록하고 넘어가라. **1번 산출물이 본체다.**

### B-1. 미분류 39건의 모델 분포

미분류(`기타 > 미분류 > 기타`)로 떨어진 39건이 규칙에서 나온 것인지 언어모델에서
나온 것인지 확인한다. 전부 `rule`이면 "규칙이 못 잡아 미분류로 남은 것"이고,
`openai`가 섞여 있으면 "언어모델도 판단하지 못한 것"이라 논문 서술이 달라진다.

```sql
SELECT ic.model_name, COUNT(*) AS cnt, ROUND(AVG(ic.confidence),4) AS avg_conf
FROM item_classification ic
JOIN category cl ON cl.category_id = ic.category_id
JOIN category cp ON cp.category_id = cl.parent_id
WHERE cp.name_ko = '미분류'
GROUP BY ic.model_name;
```

### B-2. 룰 단독 커버리지 6건 불일치

기존 실험 결과의 **룰 단독 54.3%(≈431건)** 와 커버리지 표의 **rule 437건** 이 6건 어긋난다.
논문에 두 수치가 함께 실리므로 원인 규명이 필요하다.

```sql
SELECT model_name, COUNT(*) AS cnt FROM item_classification GROUP BY model_name;

SELECT COUNT(*) AS 분류레코드없는물품
FROM auction_item ai
LEFT JOIN item_classification ic USING (pbac_no, pbac_srno, cmdt_ln_no)
WHERE ic.pbac_no IS NULL;
```

원인 후보: (a) 룰 단독 실험이 미분류를 커버리지에서 제외했다 (b) 두 수치의 측정
시점이 다르다 (c) 분류 레코드가 없는 물품이 존재한다.
**어느 쪽인지 판단해서 한 줄로 기록하라.** 확정하지 못하면 "미확정"이라고 쓰라.

### B-3. 동의어 오탐 수정 검증

`db/seed_synonym_extend.sql`에 `AR → 증강현실 / 스마트글라스` 동의어가 있었고,
이것이 `SKIN C`**`AR`**`E` 같은 물품명에 부분 매칭되어 497건 중 54건의 검색 토큰을
오염시키던 결함이 있었다. 수정되었다고 들었으나 실제 DB에 반영됐는지 확인한다.

```sql
SELECT token, COUNT(*) AS cnt
FROM item_search_token
WHERE token IN ('증강현실','스마트글라스')
GROUP BY token;
```

**기대: 0행.**

0행이 아니면 **토큰을 재적재하지 말고 그 사실을 기록만 하라.**
재적재하면 §2에서 고정한 기준점이 바뀌어 다른 모든 측정이 무효가 된다.

### B-4. 좌표 없는 세관

앱의 "전국 세관 현황" 지도 기능 관련. `schema_patch_v4`/`v5`에서 8곳만 좌표를
시딩했는데 논문에는 대상 세관이 10곳으로 되어 있어 확인이 필요하다.

```sql
SELECT COUNT(*) AS 전체세관,
       SUM(CASE WHEN latitude IS NULL OR longitude IS NULL THEN 1 ELSE 0 END) AS 좌표없음
FROM customs_office;

SELECT cstm_sgn, cstm_name FROM customs_office
WHERE latitude IS NULL OR longitude IS NULL;
```

**좌표를 채워 넣지 마라.** 비어 있다는 사실이 논문 5장의 한계 서술 재료다.

### B-5. 이미지 보유율

## 5. 단계 C — 검색 실험 재측정

논문 표 5를 완성하기 위한 측정 2종이다.

### 5.1 C-1. 영문 전용 모집단에서 0건 질의 수

**왜 필요한가**: 현재 표 5는 전체 794건 모집단에서만 측정되어 있다. 그런데 논문의
핵심 주장은 *"영문으로만 표기된 물품은 한글로 검색되지 않는다"* 이고, 그 주장이
**직접 성립하는 모집단**은 물품명이 영문·숫자로만 된 부분집합이다. 한글 표기 물품이
섞이면 기존 방식으로도 검색이 되어 두 방식의 차이가 희석된다.
"유리한 모집단에서 재지 않았다"는 지적을 막기 위해 부분집합에서 한 번 더 측정한다.

**모집단 정의**

```sql
SELECT COUNT(*) AS 영문전용건수
FROM auction_item
WHERE cmdt_nm NOT REGEXP '[가-힣]';        -- 파악된 값 243건

SELECT pbac_no, pbac_srno, cmdt_ln_no, cmdt_nm
FROM auction_item WHERE cmdt_nm NOT REGEXP '[가-힣]';
```

카운트가 243이 아니면 그 값을 그대로 기록하라. 243에 맞추려고 조건을 바꾸지 마라.

**측정**

- 질의셋: **기존 실험에서 쓴 한글 질의 20개를 그대로.** 새로 만들면 표 5의 1행과
  비교가 불가능해진다. 기존 질의셋은 `Additional_Experiment/` 이하 E03 실험
  스크립트나 설정에 있다. 찾지 못하면 HALT하고 사용자에게 물어라.
- 기존 방식: `SELECT ... FROM auction_item WHERE cmdt_nm LIKE '%<질의>%'`,
  단 모집단을 영문 전용으로 한정
- 제안 방식: Meilisearch 인덱스 `auction_items` 검색 후 결과를 영문 전용 PK 집합으로 필터
- 각 방식에서 **반환 건수가 0인 질의의 개수**를 센다

### 5.2 C-2. 질의당 반환 건수 (신규 측정)

**왜 필요한가**: 표 5는 "0건 질의 7 → 0"만 보여준다. 이건 재현율 증거다.
여기서 나올 가장 날카로운 반문은 *"쓸모없는 결과를 대량으로 뱉어서 0건을 없앤 것
아닌가?"* 이다. 카테고리 토큰을 전 물품에 부여했으므로 근거 없는 의심이 아니다.

원래는 P@5(상위 5건 정확도)로 답해야 하지만 2인 독립 관련성 판정이 필요해
논문에서 제외했다. **대신 사람 판정이 전혀 개입하지 않는 기계적 지표로
질의당 반환 건수를 측정한다.**

> **결과가 나쁘게 나와도 그대로 보고하라.** 특정 질의가 수백 건을 반환하더라도
> 조정하거나 질의를 교체하지 마라. 값이 좋으면 "무차별 매칭이 아니다"의 근거가 되고,
> 나쁘면 논문 5장의 한계 서술로 쓴다. **어느 쪽이든 논문은 성립한다.**
> 손대는 순간에만 성립하지 않는다.

**측정**

- 모집단: **전체 794건** (영문 전용도 함께 재면 더 좋다)
- 질의셋: C-1과 동일한 한글 질의 20개
- 기존 방식과 제안 방식 각각에 대해 **질의별 반환 건수**를 기록

### 5.3 산출물 명세

**중앙값·최대값을 미리 계산하지 마라. 원자료를 그대로 내라.**
집계는 논문 작성 측에서 하고 교차 검증한다.

`search_query_counts.csv` — 40행 (20질의 × 2모집단)

```csv
query,population,baseline_count,proposed_count
와인,all,0,37
와인,en_only,0,12
```

| 컬럼 | 값 |
|---|---|
| `query` | 한글 질의 문자열 |
| `population` | `all` (794건) 또는 `en_only` (영문 전용) |

### 5.4 스크립트 수정 규칙

이 단계는 실험 스크립트 수정이 필요하다. 아래를 지켜라.

- 수정 범위는 `Additional_Experiment/` 이하로 한정
- **기존 실행 결과를 덮어쓰지 마라.** 새 실험 ID 디렉터리로 분리
  (예: `Additional_Experiment/results/E03c/`)
- 검색 로직 자체(`meiliModel.js`, 토큰 가중치, 인덱스 설정, 랭킹 규칙)는 건드리지 마라.

- Meilisearch 검색 시 `limit` 기본값(보통 20) 때문에 반환 건수가 잘리지 않도록
  `estimatedTotalHits` 또는 충분히 큰 `limit`을 사용하라. 이 부분을 반드시 확인하라 —
  **잘린 건수를 그대로 기록하면 측정이 무의미해진다.**

## 부록 B. 이미 확정된 규칙 단계 결과

**대조 확인용이다. 이 수치는 논문에 이미 실려 있으므로 재측정하거나 고치지 마라.**
저장소의 `classification/rules.yaml`을 그대로 불러 표본 100건에 태운 값이다.

- 룰 매칭: 100건 중 **49건** (나머지 51건은 언어모델 단계로 이관)
- 매칭 49건 중 전체 경로 일치 **45건 (91.8%)**, 대분류 일치 47건 (95.9%)

| 물품명 | 자동 분류 | 정답 | 매칭 키워드 | 원인 |
|---|---|---|---|---|
| …HYERES LOR **에센스**실버 … (귀걸이·목걸이) | 화장품 > 스킨케어 | 주얼리 | `에센스` | 한글 부분문자열 오매칭 |

앞의 두 건은 명백한 결함, 뒤의 두 건은 경계 사례로 논문에 나누어 서술되어 있다.
개선 방향은 5장 향후과제에 적혀 있다. **지금 고치면 논문 서술과 코드가 어긋난다.**

## 부록 C. 라벨링 방법론

정답 라벨이 어떻게 만들어졌는지 묻는 경우를 위한 것이다. 논문 서술 원문:

> 정답 라벨은 자동 분류 결과를 보지 않은 상태에서 부여하였다. 라벨링 효율을 위해
> 1차 라벨은 언어모델의 보조로 작성하고 저자 1인이 100건 전수를 검토·수정하였으며,
> 판단이 어려운 물품도 유보하지 않고 대응하는 소분류가 없는 경우 대분류 또는
> 중분류까지만 부여하여 전 건을 확정하였다. 소분류에 미치지 않는 라벨 9건은
> 해당 깊이까지만 비교하는 접두 일치로 채점하였다. 다만 1차 라벨 작성에 사용한
> 언어모델은 본 시스템의 2단계 분류기와 계열이 같아 편향이 개입할 수 있으므로,
> 전수 검토를 거쳤음에도 정확도 수치는 보수적으로 해석하여야 한다.

"1인 수동 블라인드 라벨링"이라고 쓰지 않은 이유가 이것이다. 시스템 2단계가
gpt-4o-mini인데 1차 라벨도 언어모델이 작성했으므로, 숨기면 방어가 안 되고
밝히면 한계 서술로 기능한다.
